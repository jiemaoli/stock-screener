# Stock Screener 中文部署与使用指南

本文档针对当前 VPS 生产环境，说明系统的运行机制、选股逻辑、配置方式、部署更新、日常运维和故障排查。

> 风险提示：这是技术分析和候选股票筛选工具，不是自动交易系统，也不构成投资建议。数据可能延迟、缺失或错误，信号应结合风险承受能力人工复核。

## 1. 生产环境概览

| 项目 | 当前值 |
|---|---|
| 访问地址 | `https://stock-min.hhxs.top` |
| VPS 应用目录 | `/root/apps/stock-screener` |
| Compose 文件 | `/root/apps/stock-screener/deploy/docker-compose.yml` |
| Nginx 配置 | `/root/infrastructure/nginx/conf.d/stock-min.conf` |
| Docker 网络 | `infrastructure_infra-net` |
| Web 容器 | `stock-screener-dashboard` |
| 定时任务容器 | `stock-screener-scheduler` |
| 生产时区 | `America/New_York` |
| 数据持久化 | `/root/apps/stock-screener/data` |

域名由 Cloudflare 解析到 VPS，HTTPS 由现有 Nginx 容器统一处理。账号登录、会话和退出由 Flask 应用处理，应用容器不直接暴露公网端口。

## 2. 系统架构和运行流程

```text
浏览器
  → Cloudflare DNS / HTTPS
  → nginx-proxy（HTTPS 反向代理）
  → Flask 登录会话
  → stock-screener-dashboard:5050
  → 启动后台扫描进程
  → Yahoo Finance / NASDAQ 数据源
  → data/daily_scans 报告
  → Telegram Bot 消息

stock-screener-scheduler
  → 读取 data/config/schedule.json
  → 按界面配置的美东时间执行
  → 执行同一套全量扫描
```

`dashboard` 使用 Gunicorn 运行 Flask Web 页面；`scheduler` 使用同一个 Docker 镜像，每 20 秒重新读取持久化定时配置。两个容器共享 `data` 目录和 `.env`，因此扫描报告、缓存、日志、调度配置和任务锁互通。

Web 端启动扫描后会立即返回，扫描在后台继续。页面每 5 秒查询一次 `/api/scan-status`，不再让 Cloudflare/Nginx 的 HTTP 请求一直等待全量扫描。

Dashboard 已提供中文的“系统运行机制与选股规则”区域，可直接查看定时任务、实际扫描命令、全量扫描耗时原因、初筛参数、市场门槛、Minervini 规则、评分权重和技术指标解释。

## 3. Test Scan 和 Full Scan

### Test Scan

- 只扫描股票列表的前 100 只。
- 适合检查数据源、报告、页面和代码是否正常。
- 测试报告单独保存为 `test_scan_*`，不会覆盖 Dashboard 展示的最新正式全量扫描结果。
- 默认不发 Telegram，避免把测试结果当成正式信号；可在“定时任务与 TG 推送”中单独开启。

### Full Scan

- 默认扫描“标普 500 + 纳斯达克 100”的并集并去重，约 500 多只高流动性大盘股。
- 可在 Dashboard 的“定时任务与 TG 推送 → 扫描配置”切换为仅标普 500、仅纳斯达克 100或原来的全部美股。
- 原全部美股逻辑完整保留：仍从 NASDAQ Trader 获取 NASDAQ/NYSE/AMEX 上市证券目录并缓存 1 天，切换股票池不会删除历史行情缓存。
- 生成完整市场宽度、买入信号、卖出信号和个股详细理由。
- Dashboard 和 Telegram 默认只展示每类 Top 20，数量可配置为 5–100；完整排序保存在同名 JSON 审计报告中。

两个按钮都有二次确认。同一时间只允许一个扫描运行，Web 手动扫描和 scheduler 定时扫描共用 `/app/data/.scan.lock`，重复点击或时间重叠会被拒绝。

Dashboard 默认展示最新正式全量扫描结果，并保留历史全量扫描下拉框；测试扫描不会进入正式历史列表。

## 4. 每日自动扫描

在 Dashboard 的“定时任务与 TG 推送” Tab 中可配置启停状态、执行星期和美东执行时间。默认为周一至周五美东时间 18:15。页面会显示下一次运行的美东时间和对应北京时间。默认对应：

- 美国夏令时：次日 06:15。
- 美国冬令时：次日 07:15。

时区转换使用 `America/New_York` 和 `Asia/Shanghai` 时区规则自动处理，不需要每年手工改时差。设置保存到 `data/config/schedule.json`，调度容器会自动读取，无需重启。

## 5. Full Scan 性能和五年增量缓存

是的，按当前的生产命令，每天的全量扫描通常都会比较久。主要原因不是 VPS 页面，而是数据获取策略：

1. 系统仍需对股票池中的标的逐只请求 Yahoo Finance。
2. 每只股票都下载 5 年日线，用于排除 5 年内最大回撤超过 90% 的标的；真正的技术分析主要使用最近约 252 个交易日。
3. 生产使用 `--conservative`：2 个工作线程、1 秒延迟。代码内的全局锁会将外部价格请求实际上串行化，以降低 Yahoo 限流风险。
4. 首次运行会建立五年价格缓存；后续运行只下载最近 10 个交易日左右的数据并合并去重。
5. Yahoo 返回慢、重试、限流或某些 ticker 数据异常都会增加总时间。

默认指数并集模式通常约需 **10–20 分钟**；切回全部美股后仍可能需要 **60–90 分钟或更长**。增量缓存显著减少传输数据量，但每只股票仍需要一次更新请求，所以股票池大小仍是总耗时的主要因素。

当前缓存保护机制：

- 每只股票保留滚动五年日线，并留少量日期缓冲。
- 日常下载使用重叠窗口，合并后按交易日期去重。
- 默认每 30 天完整下载并校验一次历史。
- 检测到新的拆股事件时立即重建完整五年历史，避免混用不同复权基准。
- 增量请求失败时保留已有缓存；缓存不存在或损坏时重新完整下载。
- 缓存文件原子写入，避免容器中断产生半写文件。

## 6. 股票池和初筛

Dashboard 可配置四种股票池：

- 标普 500 + 纳斯达克 100（默认，并集去重）。
- 仅标普 500。
- 仅纳斯达克 100。
- 全部美股（原有模式）。

两个指数成分列表每天更新缓存；获取失败时优先使用上一次成功缓存。原全部美股模式从 NASDAQ 和其他美国交易所目录获取代码，独立缓存 1 天。两类缓存互不覆盖，因此随时可以回退。

全部美股模式构建股票池时会排除：

- 含特殊字符的代码。
- 权证、权利、单位、优先股等常见后缀。
- 通过名称关键字识别的 ETF、基金、信托、指数、债券等。
- 不符合 1–5 个大写英文字母格式的代码。

对每只股票的初筛条件：

- 价格历史至少 200 个交易日。
- 当前价格默认不低于 5 美元，不高于 10,000 美元。
- 最近 20 日日均成交量至少 100,000 股。
- 5 年历史最大回撤不得低于 -90%（即排除曾下跌超过 90% 的标的）。

## 7. 市场环境过滤

系统先分析 SPY，再统计所有通过初筛股票的市场宽度。

四阶段大致含义：

- Phase 1：筑底/盘整。
- Phase 2：上升趋势。
- Phase 3：派发/见顶。
- Phase 4：下降趋势。

只有同时满足以下条件才会计算买入信号：

- SPY 处于 Phase 1 或 Phase 2。
- 市场中处于 Phase 2 的股票占比至少 15%。

卖出信号不受这个开关限制，在任何市场环境下都会检查。

## 8. 买入选股逻辑

个股首先必须：

1. 处于 Phase 2，Phase 1 不会被当作正式买入信号。
2. 通过 Minervini Trend Template 8 条中至少 7 条。

8 条趋势模板包括：

1. 股价高于 150 日和 200 日均线。
2. 150 日均线高于 200 日均线。
3. 200 日均线在最近至少一个月向上。
4. 50 日均线高于 150 日均线，且 150 日高于 200 日。
5. 股价高于 50 日均线。
6. 股价至少比 52 周低点高 30%。
7. 股价距 52 周高点不超过 25%。
8. 相对强度达到要求。

通过硬性门槛后，代码再计算最高 125 分的综合得分：

| 项目 | 最高分 | 主要含义 |
|---|---:|---|
| 趋势结构 | 40 | 均线位置和斜率、突破、过度延伸惩罚 |
| 基本面 | 40 | 营收、EPS、库存变化和当前预留的利润率分值 |
| 风险收益比 | 15 | 以止损与预计上行目标计算 R/R |
| 相对强度 | 10 | 相对 SPY 的表现趋势 |
| 成交量 | 10 | 近期上涨日与下跌日的量能比较 |
| 入场质量 | 5 | 距高点、均线和理想入场区的位置 |
| VCP 加分 | 5 | 波动率收缩形态的质量 |

当前生产代码的真实买入信号门槛是 **总分 >= 60**。

### 关于 60 分与 70 分的说明

仓库中一些旧说明和 `config.yaml` 写的是 70 分，但 VPS 生产命令运行 `run_optimized_scan.py`，该路径实际在 `src/screening/signal_engine.py` 中以 60 分判定。`config.yaml` 属于旧的 `scripts/run_quant_engine.py` 流程，并不会被生产全市场扫描读取。

如果要将生产门槛改为 70，需要明确修改代码并重新构建镜像，不能只改 `config.yaml`。

## 9. 卖出信号

卖出扫描主要检查 Phase 3 和 Phase 4 标的，结合阶段恶化、均线跌破、相对强度走弱、成交量和基本面。总分上限 100，达到 60 分才输出卖出信号：

- 60–69：Medium。
- 70–79：High。
- 80–100：Critical。

## 10. 数据与缓存

主要持久化目录：

| 目录/文件 | 用途 |
|---|---|
| `data/daily_scans/` | Top N 文本报告、完整 JSON 审计报告及 latest 文件 |
| `data/fundamentals_cache/` | 基本面 JSON 缓存 |
| `data/cache/us_stock_universe.pkl` | 原全部美股股票池缓存 |
| `data/cache/index_stock_universes.pkl` | 标普 500、纳斯达克 100及并集缓存 |
| `data/cache/price_history_5y/` | 每只股票滚动五年行情缓存 |
| `data/config/scan_settings.json` | 股票池模式、Top N 和缓存参数 |
| `data/logs/scheduler.log` | 定时扫描日志 |
| `data/logs/web_scan_*.log` | Web 手动扫描日志 |
| `data/logs/scan_job.json` | Web 页面显示的最近任务状态 |
| `data/.scan.lock` | 防止并发扫描的文件锁 |

价格数据采用首次五年全量、日常增量、每 30 天完整校验的策略。基本面缓存采用财报季感知策略：

- 财报季时，超过 7 天刷新。
- 非财报季时，超过 90 天刷新。

## 11. Telegram 通知

Dashboard 的“定时任务与 TG 推送”页面可以配置：

- 是否启用 Telegram 推送
- Bot Token
- Chat ID
- 正式 Full Scan 和定时扫描是否推送
- 测试扫描是否推送
- 保存后立即发送测试消息

配置保存在：

```text
/root/apps/stock-screener/data/config/telegram.json
```

注意：

- Bot Token 默认以密码形式隐藏，可点击输入框右侧的小眼睛显示或再次隐藏。只有已登录 Dashboard 的用户才能读取该设置。
- Bot 需已加入目标群组/频道，并具有发消息权限。
- 配置保存后无需重启 dashboard 或 scheduler 容器。
- 原 `.env` 中的 `TELEGRAM_*` 配置仍作为首次默认值，首次在 UI 保存后会写入持久化配置文件。
- fin_twt 内部接口触发的扫描强制不发送 Telegram，不受 UI 开关影响。
- 扫描失败时目前只写日志，不会发“失败通知”。
- 通知失败不会让整个扫描失败，但错误会记录到扫描日志。
- `telegram.json` 包含 Bot Token，必须保持仅 root 可读，并且不得提交到 Git。

## 12. Web 账号登录

Dashboard 使用 Flask 会话登录，支持登录页和退出。用户名默认为 `stock`，首次迁移会使用原 Basic Auth 的初始凭据，但 `.env` 只保存 Werkzeug 密码哈希，不保存明文密码：

```dotenv
DASHBOARD_USERNAME=stock
DASHBOARD_PASSWORD_HASH=...
FLASK_SECRET_KEY=...
SESSION_COOKIE_SECURE=true
```

修改密码时应生成新的 Werkzeug 密码哈希并更新 `.env`，然后重建 dashboard 容器。`FLASK_SECRET_KEY` 用于签名会话 Cookie，必须保密且不得提交到 Git。

## 13. 生产配置方式

当前生产扫描参数主要来自命令行和代码默认值：

```bash
python run_optimized_scan.py --conservative --git-storage --clear-progress
```

| 参数 | 作用 |
|---|---|
| `--conservative` | 2 线程、1.0 秒延迟，优先降低限流风险 |
| `--git-storage` | 使用持久化基本面缓存 |
| `--clear-progress` | 每天从新一轮扫描开始，不误用前一天的分批进度 |
| `--test-mode` | 只扫前 100 只 |
| `--min-price` | 最低价格，默认 5 |
| `--min-volume` | 20 日平均最低成交量，默认 100000 |
| `--use-fmp` | 为信号股票启用 FMP 增强基本面，需 `FMP_API_KEY` |

`.env.example` 是配置模板。生产 `.env` 只放在 VPS，并且被 `.gitignore` 和 `.dockerignore` 排除。

## 14. 发布模式

本项目与 finTwt 一样采用“本机打包、上传 VPS、VPS 构建镜像”的发布方式。GitHub 只用于代码备份和版本管理，不参与 VPS 发布；VPS 不保留 `.git`、Deploy Key 或 GitHub 访问凭据。

本机在项目根目录执行：

```powershell
.\scripts\package_deploy.ps1
```

默认生成：

```text
D:\Projects\stock_screener_deploy.tar.gz
```

发布包不包含 `.git`、`.env`、凭据、历史报告、日志和缓存。

上传到 VPS：

```powershell
scp -i C:\Users\Jerry\.ssh\id_ed25519 -P 56787 `
  D:\Projects\stock_screener_deploy.tar.gz `
  root@192.210.254.31:/root/apps/
```

执行发布：

```powershell
ssh -i C:\Users\Jerry\.ssh\id_ed25519 -p 56787 root@192.210.254.31 `
  "tar -xzf /root/apps/stock_screener_deploy.tar.gz -C /root/apps/stock-screener ./scripts/deploy.sh && chmod +x /root/apps/stock-screener/scripts/deploy.sh && /root/apps/stock-screener/scripts/deploy.sh"
```

发布脚本会：

1. 保留 VPS 已有 `.env` 和 `data/`。
2. 将新代码包解压到 `/root/apps/stock-screener`。
3. 在 VPS 上重新构建 Docker 镜像并滚动重启。
4. 检查并重载 Nginx。
5. 删除 VPS 上的 `.git`、GitHub 部署密钥和已上传的发布包。

### 首次建立运行目录

以现有 VPS 目录结构为准：

```bash
mkdir -p /root/apps/stock-screener/data
cd /root/apps/stock-screener
# 由本机发布包提供应用文件，不在 VPS git clone
cp .env.example .env  # 仅首次初始化
chmod 600 .env
```

编辑 `.env` 配置 Dashboard 登录等基础私密变量，然后：

```bash
mkdir -p data/cache data/daily_scans data/fundamentals_cache data/logs
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps
```

将 `deploy/nginx-stock-min.conf` 安装到现有 Nginx 配置目录，然后检查并重载：

```bash
docker exec nginx-proxy nginx -t
docker exec nginx-proxy nginx -s reload
```

## 17. 故障排查

### 页面打不开

```bash
docker ps
docker compose -f /root/apps/stock-screener/deploy/docker-compose.yml ps
docker logs --tail=200 stock-screener-dashboard
docker logs --tail=200 nginx-proxy
docker exec nginx-proxy nginx -t
```

同时检查 Cloudflare DNS 是否指向正确 VPS，Nginx 证书是否包含该域名。

### 扫描一直显示 running

```bash
cat /root/apps/stock-screener/data/logs/scan_job.json
docker top stock-screener-dashboard
docker top stock-screener-scheduler
```

不要因为页面断开就直接再点一次 Full Scan。先检查进程和日志；文件锁会阻止大多数重复任务。

### 扫描失败

1. 在 `scan_job.json` 中查看 `log` 字段。
2. 打开对应的 `data/logs/web_scan_*.log`。
3. 搜索 `Fatal error`、`Traceback`、`429`、`rate limit`和 `Too Many Requests`。
4. 检查 VPS 磁盘、内存和 Docker 容器状态。

```bash
df -h
free -h
docker stats --no-stream
```

### 有部分 ticker 报错

单个 ticker 的数据缺失或格式异常会被记录并跳过，不一定会使整轮扫描失败。报告中会显示总错误率。如果错误率明显升高，优先检查 Yahoo 限流或上游数据格式变化。

### Telegram 没有消息

- 在“定时任务与 TG 推送”中确认已启用推送，并开启对应的正式扫描或测试扫描开关。
- 确认 Bot 在群里并有发言权限。
- 点击“保存并测试”，根据页面提示检查 Bot Token 和 Chat ID。
- 检查 `data/config/telegram.json` 是否存在且容器可读。
- 在扫描日志中搜索 `Telegram notification failed`。

## 18. 回滚

优先使用 Git 的已知正常提交回滚，不删除持久化 `data` 目录：

```bash
cd /root/apps/stock-screener
git log --oneline -10
git switch --detach <known-good-commit>
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d
```

验证恢复后，再决定是否建立修复分支或返回 `main`。不要在未备份的情况下删除 `data`、`.env`、Nginx 密码文件或证书。

## 21. fin_twt 内部筛选接口

`fin_twt` 和 `stock-screener-dashboard` 都连接到 Docker 网络
`infrastructure_infra-net`。`fin_twt` 应直接访问：

```text
http://stock-screener-dashboard:5050
```

不要从 `fin_twt` 绕行公网域名。Nginx 会对公网请求的 `/internal/` 路径返回
404，Flask 内部接口还会校验 `.env` 中的 `SCREENER_API_TOKEN`。

### 创建筛选任务

```http
POST /internal/v1/screenings
Authorization: Bearer <SCREENER_API_TOKEN>
Content-Type: application/json

{
  "tickers": ["AAPL", "MSFT", "NVDA"],
  "result_limit": 20
}
```

接口返回 HTTP 202 和 `job_id`。也可以显式传入 `{"universe":"configured"}`，
扫描 Dashboard 当前配置的完整股票池；完整股票池任务通常需要 10–20 分钟，调用方
必须异步轮询，不能同步等待 HTTP 请求完成。

每次最多提交 600 个 ticker。股票代码会转为大写、去重并校验，只允许字母、数字、
点和连字符。

### 查询状态和结果

```http
GET /internal/v1/screenings/<job_id>
Authorization: Bearer <SCREENER_API_TOKEN>
```

状态为 `running`、`completed` 或 `failed`。完成后响应会包含 `result`，其中包括：

- `statistics`
- `buy_signals`
- `sell_signals`
- `spy_analysis`
- `breadth`

接口任务强制使用 `--no-telegram`，不会发送 Telegram；报告保存在
`data/api_scans/<job_id>/`，不会覆盖 Dashboard 的正式报告、历史下拉框或测试报告。
接口任务和网页、定时扫描共用 `data/.scan.lock`，同时只能运行一个扫描任务；冲突时
返回 HTTP 409。
