# Stock Screener 中文部署与使用指南

本文档针对当前 VPS 生产环境，说明系统的运行机制、选股逻辑、配置方式、部署更新、日常运维和故障排查。

> 风险提示：这是技术分析和候选股票筛选工具，不是自动交易系统，也不构成投资建议。数据可能延迟、缺失或错误，信号应结合风险承受能力人工复核。

## 1. 生产环境概览

| 项目 | 当前值 |
|---|---|
| 访问地址 | `https://stock-min.hhxs.top` |
| VPS 应用目录 | `/root/apps/stock-screener` |
| Compose 文件 | `/root/apps/stock-screener/deploy/docker-compose.yml` |
| Nginx 配置 | `/root/infrastructure/nginx/conf.d/stock-min.conf` |
| Docker 网络 | `infrastructure_infra-net` |
| Web 容器 | `stock-screener-dashboard` |
| 定时任务容器 | `stock-screener-scheduler` |
| 生产时区 | `America/New_York` |
| 数据持久化 | `/root/apps/stock-screener/data` |

域名由 Cloudflare 解析到 VPS，HTTPS 和 Basic Auth 由现有 Nginx 容器统一处理。应用容器不直接暴露公网端口。

## 2. 系统架构和运行流程

```text
浏览器
  → Cloudflare DNS / HTTPS
  → nginx-proxy（Basic Auth）
  → stock-screener-dashboard:5050
  → 启动后台扫描进程
  → Yahoo Finance / NASDAQ 数据源
  → data/daily_scans 报告
  → Telegram Bot 消息

stock-screener-scheduler
  → cron（美东时间工作日 18:15）
  → 执行同一套全量扫描
```

`dashboard` 使用 Gunicorn 运行 Flask Web 页面；`scheduler` 使用同一个 Docker 镜像，但前台运行 cron。两个容器共享 `data` 目录和 `.env`，因此扫描报告、缓存、日志和任务锁互通。

Web 端启动扫描后会立即返回，扫描在后台继续。页面每 5 秒查询一次 `/api/scan-status`，不再让 Cloudflare/Nginx 的 HTTP 请求一直等待全量扫描。

## 3. Test Scan 和 Full Scan

### Test Scan

- 只扫描股票列表的前 100 只。
- 适合检查数据源、报告、页面和代码是否正常。
- 默认不发 Telegram，避免把测试结果当成正式信号。
- 可通过 `TELEGRAM_NOTIFY_TEST=true` 允许测试通知。

### Full Scan

- 扫描 NASDAQ/NYSE/AMEX 股票池经过基础过滤后的全部标的，当前约 3,700–3,800 只。
- 生成完整市场宽度、买入信号、卖出信号和个股详细理由。
- 扫描成功后向 Telegram 发送市场状态、BUY 代码列表和 SELL 代码列表。

两个按钮都有二次确认。同一时间只允许一个扫描运行，Web 手动扫描和 cron 定时扫描共用 `/app/data/.scan.lock`，重复点击或时间重叠会被拒绝。

## 4. 每日自动扫描

定时规则在 `deploy/stock-screener.cron`：

```cron
15 18 * * 1-5
```

即周一至周五美东时间 18:15，在美股收盘后运行。对应北京时间：

- 美国夏令时：次日 06:15。
- 美国冬令时：次日 07:15。

时区转换由容器的 `America/New_York` 时区自动处理，不需要每年手工改 cron。周一至周五包括美股休市日；休市时数据可能与前一交易日相同。

## 5. 为什么 Full Scan 很慢

是的，按当前的生产命令，每天的全量扫描通常都会比较久。主要原因不是 VPS 页面，而是数据获取策略：

1. 对约 3,761 只股票逐只请求 Yahoo Finance。
2. 每只股票都下载 5 年日线，用于排除 5 年内最大回撤超过 90% 的标的；真正的技术分析主要使用最近约 252 个交易日。
3. 生产使用 `--conservative`：2 个工作线程、1 秒延迟。代码内的全局锁会将外部价格请求实际上串行化，以降低 Yahoo 限流风险。
4. 价格历史为了保证当日信号，每次都会重新获取。基本面会缓存，但不能省掉价格请求。
5. Yahoo 返回慢、重试、限流或某些 ticker 数据异常都会增加总时间。

按当前保守配置，常见时间是 **60–90 分钟或更长**，每天会随网络和 Yahoo 状态波动。基本面缓存命中可减少部分请求，但现有实现仍会逐只刷新 5 年价格，所以第二天不会突然变成几分钟。

可选优化方向（需先测试准确性和限流风险）：

- 使用 yfinance 批量下载，减少逐 ticker HTTP 开销。
- 本地持久化价格历史，每日只增量补最新 K 线。
- 将“5 年严重回撤检查”和“日常技术扫描”分层，不必每天重算 5 年历史。
- 谨慎将生产模式从 conservative 调整为默认或 aggressive；速度会提高，但 429 限流和缺数据风险也会提高。
- 做增量失败队列，只重试本次失败的 ticker。

## 6. 股票池和初筛

全量扫描从 NASDAQ 和其他美国交易所列表获取代码，股票池缓存 1 天。构建股票池时会排除：

- 含特殊字符的代码。
- 权证、权利、单位、优先股等常见后缀。
- 通过名称关键字识别的 ETF、基金、信托、指数、债券等。
- 不符合 1–5 个大写英文字母格式的代码。

对每只股票的初筛条件：

- 价格历史至少 200 个交易日。
- 当前价格默认不低于 5 美元，不高于 10,000 美元。
- 最近 20 日日均成交量至少 100,000 股。
- 5 年历史最大回撤不得低于 -90%（即排除曾下跌超过 90% 的标的）。

## 7. 市场环境过滤

系统先分析 SPY，再统计所有通过初筛股票的市场宽度。

四阶段大致含义：

- Phase 1：筑底/盘整。
- Phase 2：上升趋势。
- Phase 3：派发/见顶。
- Phase 4：下降趋势。

只有同时满足以下条件才会计算买入信号：

- SPY 处于 Phase 1 或 Phase 2。
- 市场中处于 Phase 2 的股票占比至少 15%。

卖出信号不受这个开关限制，在任何市场环境下都会检查。

## 8. 买入选股逻辑

个股首先必须：

1. 处于 Phase 2，Phase 1 不会被当作正式买入信号。
2. 通过 Minervini Trend Template 8 条中至少 7 条。

8 条趋势模板包括：

1. 股价高于 150 日和 200 日均线。
2. 150 日均线高于 200 日均线。
3. 200 日均线在最近至少一个月向上。
4. 50 日均线高于 150 日均线，且 150 日高于 200 日。
5. 股价高于 50 日均线。
6. 股价至少比 52 周低点高 30%。
7. 股价距 52 周高点不超过 25%。
8. 相对强度达到要求。

通过硬性门槛后，代码再计算最高 125 分的综合得分：

| 项目 | 最高分 | 主要含义 |
|---|---:|---|
| 趋势结构 | 40 | 均线位置和斜率、突破、过度延伸惩罚 |
| 基本面 | 40 | 营收、EPS、库存变化和当前预留的利润率分值 |
| 风险收益比 | 15 | 以止损与预计上行目标计算 R/R |
| 相对强度 | 10 | 相对 SPY 的表现趋势 |
| 成交量 | 10 | 近期上涨日与下跌日的量能比较 |
| 入场质量 | 5 | 距高点、均线和理想入场区的位置 |
| VCP 加分 | 5 | 波动率收缩形态的质量 |

当前生产代码的真实买入信号门槛是 **总分 >= 60**。

### 关于 60 分与 70 分的说明

仓库中一些旧说明和 `config.yaml` 写的是 70 分，但 VPS 生产命令运行 `run_optimized_scan.py`，该路径实际在 `src/screening/signal_engine.py` 中以 60 分判定。`config.yaml` 属于旧的 `scripts/run_quant_engine.py` 流程，并不会被生产全市场扫描读取。

如果要将生产门槛改为 70，需要明确修改代码并重新构建镜像，不能只改 `config.yaml`。

## 9. 卖出信号

卖出扫描主要检查 Phase 3 和 Phase 4 标的，结合阶段恶化、均线跌破、相对强度走弱、成交量和基本面。总分上限 100，达到 60 分才输出卖出信号：

- 60–69：Medium。
- 70–79：High。
- 80–100：Critical。

## 10. 数据与缓存

主要持久化目录：

| 目录/文件 | 用途 |
|---|---|
| `data/daily_scans/` | 每次扫描的文本报告和 `latest_optimized_scan.txt` |
| `data/fundamentals_cache/` | 基本面 JSON 缓存 |
| `data/cache/` | 股票池等运行缓存 |
| `data/logs/scheduler.log` | 定时扫描日志 |
| `data/logs/web_scan_*.log` | Web 手动扫描日志 |
| `data/logs/scan_job.json` | Web 页面显示的最近任务状态 |
| `data/.scan.lock` | 防止并发扫描的文件锁 |

价格数据每次刷新。基本面缓存采用财报季感知策略：

- 财报季时，超过 7 天刷新。
- 非财报季时，超过 90 天刷新。

## 11. Telegram 通知

VPS 上的密钥保存在：

```text
/root/apps/stock-screener/.env
```

需要的配置：

```dotenv
TELEGRAM_BOT_TOKEN=从_BotFather_获取的令牌
TELEGRAM_CHAT_ID=目标群组或频道_ID
TELEGRAM_NOTIFY_TEST=false
```

注意：

- Bot 需已加入目标群组/频道，并具有发消息权限。
- 正式 Full Scan 和 cron 扫描成功生成报告后会通知。
- 扫描失败时目前只写日志，不会发“失败通知”。
- 通知失败不会让整个扫描失败，但错误会记录到扫描日志。
- `.env` 必须设为仅 root 可读，不得提交到 Git。

修改 `.env` 后重建容器以使其读取新配置：

```bash
cd /root/apps/stock-screener
docker compose -f deploy/docker-compose.yml up -d --force-recreate dashboard scheduler
```

## 12. Web 访问与 Basic Auth

Basic Auth 由 Nginx 配置，不是 Flask 应用密码。用户名为 `stock`，初始凭据记录在 VPS：

```text
/root/apps/stock-screener/deploy/.initial_credentials
```

密码文件位于 Nginx 配置目录，不应提交到 Git。如需改密码，可在 VPS 上生成新的 htpasswd 并重载 Nginx。操作前应备份旧文件，避免把自己锁在系统外。

## 13. 生产配置方式

当前生产扫描参数主要来自命令行和代码默认值：

```bash
python run_optimized_scan.py --conservative --git-storage --clear-progress
```

| 参数 | 作用 |
|---|---|
| `--conservative` | 2 线程、1.0 秒延迟，优先降低限流风险 |
| `--git-storage` | 使用持久化基本面缓存 |
| `--clear-progress` | 每天从新一轮扫描开始，不误用前一天的分批进度 |
| `--test-mode` | 只扫前 100 只 |
| `--min-price` | 最低价格，默认 5 |
| `--min-volume` | 20 日平均最低成交量，默认 100000 |
| `--use-fmp` | 为信号股票启用 FMP 增强基本面，需 `FMP_API_KEY` |

`.env.example` 是配置模板。生产 `.env` 只放在 VPS，并且被 `.gitignore` 和 `.dockerignore` 排除。

## 14. 发布模式

本项目与 finTwt 一样采用“本机打包、上传 VPS、VPS 构建镜像”的发布方式。GitHub 只用于代码备份和版本管理，不参与 VPS 发布；VPS 不保留 `.git`、Deploy Key 或 GitHub 访问凭据。

本机在项目根目录执行：

```powershell
.\scripts\package_deploy.ps1
```

默认生成：

```text
D:\Projects\stock_screener_deploy.tar.gz
```

发布包不包含 `.git`、`.env`、凭据、历史报告、日志和缓存。

上传到 VPS：

```powershell
scp -i C:\Users\Jerry\.ssh\id_ed25519 -P 56787 `
  D:\Projects\stock_screener_deploy.tar.gz `
  root@192.210.254.31:/root/apps/
```

执行发布：

```powershell
ssh -i C:\Users\Jerry\.ssh\id_ed25519 -p 56787 root@192.210.254.31 `
  "tar -xzf /root/apps/stock_screener_deploy.tar.gz -C /root/apps/stock-screener ./scripts/deploy.sh && chmod +x /root/apps/stock-screener/scripts/deploy.sh && /root/apps/stock-screener/scripts/deploy.sh"
```

发布脚本会：

1. 保留 VPS 已有 `.env` 和 `data/`。
2. 将新代码包解压到 `/root/apps/stock-screener`。
3. 在 VPS 上重新构建 Docker 镜像并滚动重启。
4. 检查并重载 Nginx。
5. 删除 VPS 上的 `.git`、GitHub 部署密钥和已上传的发布包。

### 首次建立运行目录

以现有 VPS 目录结构为准：

```bash
mkdir -p /root/apps/stock-screener/data
cd /root/apps/stock-screener
# 由本机发布包提供应用文件，不在 VPS git clone
cp .env.example .env  # 仅首次初始化
chmod 600 .env
```

编辑 `.env` 配置 Telegram 等私密变量，然后：

```bash
mkdir -p data/cache data/daily_scans data/fundamentals_cache data/logs
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d
docker compose -f deploy/docker-compose.yml ps
```

将 `deploy/nginx-stock-min.conf` 安装到现有 Nginx 配置目录，配置 Basic Auth 后检查并重载：

```bash
docker exec nginx-proxy nginx -t
docker exec nginx-proxy nginx -s reload
```

## 15. 日常更新部署

日常更新不需要先推送 GitHub。直接使用本机当前工作区打包、SCP 上传，再运行 `scripts/deploy.sh`。如果需要留存版本记录，可以在发布前或发布后单独提交到 GitHub，但这不影响生产发布。

部署完成后在 VPS 验证：

```bash
cd /root/apps/stock-screener
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs --tail=100 dashboard
docker compose -f deploy/docker-compose.yml logs --tail=100 scheduler
curl -I https://stock-min.hhxs.top
test ! -d /root/apps/stock-screener/.git
```

未带 Basic Auth 的 `curl` 返回 `401 Unauthorized` 是正常的，说明公网访问已被保护。

## 17. 故障排查

### 页面打不开

```bash
docker ps
docker compose -f /root/apps/stock-screener/deploy/docker-compose.yml ps
docker logs --tail=200 stock-screener-dashboard
docker logs --tail=200 nginx-proxy
docker exec nginx-proxy nginx -t
```

同时检查 Cloudflare DNS 是否指向正确 VPS，Nginx 证书是否包含该域名。

### 扫描一直显示 running

```bash
cat /root/apps/stock-screener/data/logs/scan_job.json
docker top stock-screener-dashboard
docker top stock-screener-scheduler
```

不要因为页面断开就直接再点一次 Full Scan。先检查进程和日志；文件锁会阻止大多数重复任务。

### 扫描失败

1. 在 `scan_job.json` 中查看 `log` 字段。
2. 打开对应的 `data/logs/web_scan_*.log`。
3. 搜索 `Fatal error`、`Traceback`、`429`、`rate limit`和 `Too Many Requests`。
4. 检查 VPS 磁盘、内存和 Docker 容器状态。

```bash
df -h
free -h
docker stats --no-stream
```

### 有部分 ticker 报错

单个 ticker 的数据缺失或格式异常会被记录并跳过，不一定会使整轮扫描失败。报告中会显示总错误率。如果错误率明显升高，优先检查 Yahoo 限流或上游数据格式变化。

### Telegram 没有消息

- 确认是 Full Scan，或已设置 `TELEGRAM_NOTIFY_TEST=true`。
- 确认 Bot 在群里并有发言权限。
- 检查 `.env` 是否挂载到容器。
- 修改 `.env` 后要重建容器。
- 在扫描日志中搜索 `Telegram notification failed`。

## 18. 回滚

优先使用 Git 的已知正常提交回滚，不删除持久化 `data` 目录：

```bash
cd /root/apps/stock-screener
git log --oneline -10
git switch --detach <known-good-commit>
docker compose -f deploy/docker-compose.yml build
docker compose -f deploy/docker-compose.yml up -d
```

验证恢复后，再决定是否建立修复分支或返回 `main`。不要在未备份的情况下删除 `data`、`.env`、Nginx 密码文件或证书。

## 19. 备份和安全

建议备份：

- `/root/apps/stock-screener/.env`
- `/root/apps/stock-screener/data/`
- `/root/infrastructure/nginx/conf.d/stock-min.conf`
- Nginx Basic Auth 密码文件
- HTTPS 证书和私钥（按现有 infrastructure 备份策略）

安全原则：

- Telegram Bot Token、Basic Auth 密码和证书私钥不进 Git。
- `.env` 权限保持 `600`。
- 仅 Nginx 对外暴露 80/443，dashboard 通过 Docker 网络访问。
- 更新前查看 `git status`，避免覆盖 VPS 本地配置。
- 定期更换已暴露或怀疑泄露的 Bot Token 和密码。

## 20. 已知问题与待改进项

- 生产买入门槛是 60，而旧 `config.yaml` 是 70；已在本文档明确区分，但未擅自改变交易规则。
- 全量扫描逐 ticker 下载 5 年数据，是当前最大的性能瓶颈。
- 少数 ticker 可因上游数据缺失或 `None` 值比较异常而被跳过。
- 完整 pytest 中旧邮件测试可能因 Pandas/Yahoo 日期 `NaT` 写入 SQLite 而失败，与 VPS Web 扫描主流程不同。
- Telegram 目前只发扫描成功摘要，还没有扫描失败报警和报告文件附件。
